# Workflow
- Parallelize independent work phases by spawning sub-agents rather than executing sequentially to keep each agent's context clean and unpolluted. Confidence: 0.87
- When creating many similar content pages (e.g., 30+ articles), use a data-driven generator script (Node.js/Python) that reads structured JSON data and renders HTML templates, rather than crafting each page manually — the user prefers consistency and efficiency in bulk page creation. Confidence: 0.75
- For article/news content pages, use differentiated layout templates: a standard template for regular news/promotions, and a richer block-based template for inspiration/lifestyle content that features multi-column image layouts, image+text combos, and hero headers — the user expects layout variety to match content type. Confidence: 0.70
- Download reference website images locally rather than hotlinking from external CDNs — the user prefers self-hosting all site assets. Confidence: 0.65
- Use flat `.html` files in a content subdirectory (e.g., `tin-tuc/{slug}.html`) rather than `index.html` inside subdirectories — the user prefers straightforward file naming for content pages. Confidence: 0.65
- When replicating content from a reference/competitor website, faithfully reproduce the original page's layout structure including complex blocks (multi-column images, image+text combos, hero sections) rather than simplifying to a basic blog layout — the user values accurate reproduction of the reference design. Confidence: 0.70
- When batch-processing multiple files that each need customized treatment (e.g., different crop regions, dimensions, or content types), first survey all files and propose a tailored plan per file for user approval before executing the batch. Confidence: 0.70
- A Python dev server runs persistently on port 8000 for debugging — always use this running server rather than starting a new one. Confidence: 0.80
- Use sub-agents for codebase research/exploration before building — delegate discovery of existing code structure, data, and templates to sub-agents rather than doing it manually or making assumptions. Confidence: 0.70
- Use task description markdown files in `docs/tasks/` (named with date prefixes like `260725-1.1-vasta.md`) as the authoritative instruction source for what to build — reference them directly rather than restating requirements inline. Confidence: 0.80
- Iteratively refine through sequential sub-agents: first run a sub-agent for bulk generation, then visually inspect the local server output, then run a follow-up sub-agent to fix and integrate based on what was seen. Confidence: 0.70
- For static websites, serve locally with Python's built-in HTTP server (`python -m http.server <port>`) instead of complex project exploration. Confidence: 0.75
- When debugging click/interaction issues in Swiper carousels with `loop: true`, use event delegation (on `document` or a parent container) rather than per-element `addEventListener`, because Swiper clones slides and clones don't carry direct event listeners. Confidence: 0.85
- For small carousels with few (e.g. ≤5) slides, disable Swiper's `loop: false` to avoid off-screen cloned elements that intercept clicks and cause "button doesn't respond" bugs. Confidence: 0.75
- For portrait-oriented images used as landscape slide backgrounds, use `background-size: contain` with a dark `background-color` rather than `background-size: cover`, so the image letterboxes cleanly without cropping. Confidence: 0.70
- For square or landscape images used as banner/slide backgrounds, use `background-size: cover` instead of `contain` — the image fills the container without dead bars or letterbox stripes. Confidence: 0.65
- Debug visual/interaction bugs by using the browser tool (screenshot, snapshot, eval) to inspect the rendered page rather than relying solely on static code analysis. Confidence: 0.92
- When debugging a hypothesis, test ALL relevant cases/variations (e.g., all brands, all URL formats) side by side before drawing a conclusion — not just one case — to avoid incomplete or misleading analysis. Confidence: 0.70
- Verify and test implementation end-to-end before marking tasks complete; do not rely on passing initial superficial checks. Confidence: 0.80
- When updating navigation targets on a UI component (e.g., hero slides, cards), ensure ALL interactive sub-elements within that component are updated consistently — both background click targets (data-href) and visible CTA buttons/links must point to the same new destination, not just one of them. The user will notice and call out partial updates. Confidence: 0.75
- When content/data is incomplete for a page (e.g., missing images, descriptions), create the page structure with placeholders and add the content later rather than blocking development. Confidence: 0.75
- When updating asset references (images, scripts, stylesheets) across the project, proactively check and update ALL HTML pages that use those assets, not just the one the user mentioned — search for references across the entire project to ensure consistency. Confidence: 0.75
- Prefer targeted, functional improvements over cosmetic cleanup — skip non-essential refactoring or cleanup that doesn't add functional value. Confidence: 0.65
- When integrating an interactive component across multiple pages, ensure BOTH its JavaScript AND CSS dependencies are linked on every page — missing the stylesheet can cause the element to exist in the DOM but be invisible (e.g., positioned statically off-screen). Confidence: 0.70
- When debugging cached static assets during development, force a fresh load by appending a cache-busting query parameter (e.g., `?t=$(date +%s)`) to the URL rather than relying on browser reload. Confidence: 0.65
- When debugging URL/routing behavior (query strings, redirects) on a static site, first identify which dev server the user is actually running (Python http.server, `serve`, nginx, etc.) since different servers handle query strings and `index.html` redirects differently — never assume one server's behavior applies to another. Confidence: 0.75
- When the user asks to "commit and push," handle the full git workflow autonomously — stage all changes (`git add -A`), write a descriptive commit message summarizing the work, include a `Co-authored-by` trailer crediting the AI assistant, and push to the remote. The user trusts the assistant to manage the entire process without specifying commit format or scope. Confidence: 0.65
- When building out content pages (e.g., news, articles), source real content by crawling reference/competitor websites rather than using placeholder or mock data — the user values authentic, real-world content for the project. Confidence: 0.70
- When asked to remove UI items (menu entries, links, sections) that might be needed again later, prefer commenting them out in code rather than deleting them — the user says "hide it so we can remember them later." Confidence: 0.75
- Name new pages/files after the specific product, brand, or collection they represent (e.g., `tele-di-marmo-lumia.html`) rather than using abstract/conceptual/Vietnamese names (e.g., `kien-tao.html`) — the user prefers filenames that directly identify the content's subject. Confidence: 0.70
- When generated/rendered pages don't meet visual quality standards, hide the feature (comment out nav links, mark sections as hidden) rather than leaving ugly or unfinished pages visible to visitors — the user has a low tolerance for unattractive output and prefers to remove access entirely rather than keep it visible in a poor state. Confidence: 0.75
- When a UI section (navigation links, category grids, feature blocks) points to pages that don't exist yet (e.g., all links are `#` or 404 destinations), hide the entire section with a `hidden` attribute or comment rather than leaving non-functional links visible — the user proactively asks to hide such sections. Confidence: 0.70
